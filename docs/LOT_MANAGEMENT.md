# Generated lots, release and trolley mapping

Migration V8 runs automatically at startup. Existing lot UUIDs, numbers and quantities
are preserved. All new lot UUIDs and lot numbers are generated by the backend.

## Plan lots when creating a style

```http
POST /api/v1/styles
Content-Type: application/json

{
  "styleNumber":"STYLE-01",
  "description":"Production style",
  "processIds":["<process UUID>"],
  "lotCount":5,
  "quantity":100
}
```

This saves a DRAFT style with a plan for five lots, each containing 100 garments.
It creates no lots yet. `lotCount` is optional (default 0), with a range of 0–1000.
`quantity` is optional and must be positive when supplied. It applies to every lot,
not the combined total. Missing quantity is stored as null, not zero or a made-up value.
Style responses expose the plan as `lot_count` and `lot_quantity`.

Release with `POST /api/v1/styles/{id}/release`. Release saves the route and creates
all planned lots, visits and process executions in one transaction. On failure,
the whole release rolls back. Repeated release returns 409 and cannot duplicate lots.
Styles with zero planned lots release without creating any. Administrators and
Production Manager retain release access. Style Configurator can also release styles
they created, using the same POST release endpoint. Another creator's style is denied
with 403. Custom roles with New Style alone do not receive this release permission.

Generated numbers have the form `LOT-<epoch milliseconds>-<style sequence>`, for
example `LOT-1794441600000-001`, then `LOT-1794441600001-002`. Each new style starts
at 001 and advances by one for each committed lot, across release-time and later
batches. The suffix is padded to at least three digits and is never truncated or
wrapped (1000 remains 1000 if ever reached).

Migration V9 preserves every existing lot number. Existing styles continue after
the larger of their existing lot count and largest historical generated suffix;
new styles start at 001. Historical global suffixes are not rewritten. Cancelled
lots still consume their sequence position.

A row-locked per-style counter and unique `(style_id,lot_sequence)` index protect
new allocations. A factory-wide logical epoch millisecond is reserved for each lot,
using the larger of the current epoch time and the last reserved millisecond plus
one. This prevents different styles both producing the same timestamp-001 number,
including during concurrent requests or clock adjustments. The existing unique
`lot_number` constraint provides the final database safeguard against duplicates
within the factory database. Counter updates roll back with a failed creation.

The separate internal `id` remains a UUID. Do not send `lotNumber` or `id` when creating lots.
## Add more lots after release

```http
POST /api/v1/styles/{styleId}/lots
Content-Type: application/json

{"lotCount":3,"quantity":80}
```

Creates three more lots, each with quantity 80. The batch is atomic and numbers follow
the same format as release-generated lots. `lotCount` defaults to 1 and accepts 1–1000.
Omit `quantity` to leave it unset for every lot in this batch. A DRAFT style returns
409; additional lots are allowed after release, including later production stages.
Adding lots to a completed style reopens it for production.

The response is always a batch object, including when creating one lot:

```json
{"createdCount":3,"items":[{"id":"<UUID>","lot_number":"LOT-1794441600000-001","quantity":80}]}
```

`items` contains every created lot. Read the resulting inventory using the paginated
GET `/api/v1/lots` or GET `/api/v1/styles/{id}/lots`. Lot responses include nullable
`trolley_id` and `trolley_code` for the current mapping.

If an unspecified quantity is later provided by a production revision, it is saved
and audited normally. At final QC, an unset quantity is recorded from the positive
inspected total (passed + rejected). Known quantities must still match that total.
`original_quantity` remains null when the original quantity was unspecified.

## Style Configurator ownership

Style Configurator can list, read, create, edit quantity, cancel and map lots only for styles they
created. This includes lots added by an administrator to their style. The lot's own
`created_by` does not determine visibility. Other users' lots are excluded from list
results and totals; guessing an outside lot/style UUID returns 403.

The same restriction applies to `/styles/{id}/lots`, lot timelines and the paged
`styles` selector in `/api/v1/ui/lookups`. The selector includes owned released,
in-production and completed styles. NW Admin, IT Admin and Production Manager keep
their general lot access. Custom roles with New Style but no Style Management follow
the same ownership rule when granted Lot Management.

## Edit a lot's quantity

```http
PUT /api/v1/lots/{lotId}
Content-Type: application/json

{"quantity":120,"reason":"Quantity corrected after recount"}
```

All PC roles granted Lot Management can edit quantity. Style Configurator and
ownership-restricted custom roles can edit only lots belonging to their own styles.
The response is the updated lot. `quantity` is required and must be a positive integer;
`reason` is required, must contain non-whitespace text and accepts at most 500 characters.
An unspecified initial quantity can be set through this endpoint; quantity cannot be
cleared back to null.

Editing is allowed at any stage before completion, including processing, storage and
QC, except during transit (DISPATCHED). DISPATCHED, COMPLETED and CANCELLED return 409.
Other users' lots return 403 for ownership-restricted roles. Every actual change
records old/new quantity, actor and reason in quantity history and the audit log.
Repeating the current quantity succeeds without adding a duplicate change record.

Lot UUID, generated number, style, route, workflow status and `original_quantity` stay
unchanged. Edits affect only the selected lot, not sibling lots or the style's planned
quantity. Use the existing mapping calls for trolley changes. Final QC checks against
the updated quantity. No additional database migration is needed for this endpoint.

## Assign and unassign a trolley

PC users with the `lots` module can choose an available trolley using the paginated
GET `/api/v1/trolleys/available`. This does not grant trolley configuration access.

```http
PUT /api/v1/lots/{lotId}/trolley
Content-Type: application/json

{"trolleyId":"<trolley UUID>"}
```

```http
DELETE /api/v1/lots/{lotId}/trolley
```

Both calls return the updated lot. Style Configurator can use them only for owned
styles' lots. Mapping requires lot status READY, AT_STATION or READY_FOR_DISPATCH.
Inactive trolleys, occupied trolleys and already-mapped lots are rejected; unassign
before assigning a different trolley. Unassignment is idempotent and restores the
previous lot location. Trolleys cannot be removed while a lot is dispatched, processing,
stored or terminal. Row locks and unique constraints prevent concurrent double booking.

The existing operational `/lots/{id}/trolley-link`, dispatch, placement and QC routes
retain their PAD/operational permissions. Lot Management grants neither dispatch nor QC.
